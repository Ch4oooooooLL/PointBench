# PointBench 项目功能完整性、安全性与工程质量审查整改建议

> 文档用途：用于项目后续开发整改、代码审查、Agent 执行任务拆分，以及作为项目技术债和安全整改清单。  
> 适用对象：项目开发者、后端/前端维护人员、实验数据管理系统使用方。  
> 审查范围：后端接口、前端交互、文件导入导出、数据持久化、实验数据分析逻辑、安全边界、工程可维护性。  
> 当前判断：项目已经具备实验室内网 MVP 使用条件，但尚不建议直接作为生产级多人协作系统部署。

---

## 1. 项目总体评价

PointBench 当前已经形成了一个较完整的实验点位与测试数据管理闭环。项目能够承接 Android App 导出的点位数据压缩包，并在 Web 端完成项目查看、点位浏览、测试轮次管理、应变数据录入、趋势分析和数据导出。整体方向正确，功能结构与车架疲劳试验、应变片点位管理、试验数据沉淀等场景具有较高匹配度。

从目前代码和功能表现看，项目已经不是单纯的页面原型，而是具备实际业务流转能力的 MVP 系统。它可以支持实验室内部小范围试用，帮助解决点位照片记录混乱、测试数据分散、数据趋势不直观、项目资料难以复用等问题。

但如果后续希望将该系统长期用于公司实验数据管理，甚至部署到局域网供多人访问，则当前仍存在明显短板，主要集中在以下几个方面：

1. 文件上传和路径处理的安全边界不足；
2. 项目、图片、测试数据等核心对象的删除操作缺少保护；
3. 缺少用户、角色、权限和操作审计；
4. 数据校验和导入预检不足，容易引入错误实验数据；
5. 数据库结构演进能力不足，后续功能扩展会受限；
6. 异常识别规则仍偏简单，不能作为严格疲劳损伤判定依据；
7. 前端在点位较多、数据量较大时可能出现性能问题；
8. 缺少自动化测试，后续迭代容易引入回归问题。

因此，项目下一阶段不宜继续盲目增加功能，而应优先补齐安全、数据一致性、权限控制和测试体系。

## 2. 当前已经具备的核心能力

### 2.1 项目导入能力

当前项目支持从 Android App 导出的 zip 包导入数据。导入逻辑能够读取压缩包中的 `manifest.json`，并根据其中的项目信息、点位信息和图片文件在后端创建项目数据。

该能力对于实际实验流程非常关键。因为现场点位记录通常发生在移动端，而后续数据分析和报告整理更适合在桌面端完成。通过 zip 包作为中间交换格式，可以降低移动端与 Web 端之间的耦合，也便于后续通过 OA、PDM 或文件服务器传递实验资料。

建议后续继续保持该模式，但需要强化导入前预检、压缩包安全检查和导入结果报告。

### 2.2 点位管理能力

系统已经能够展示项目下的点位信息，包括点位编号、部件名称、点位备注、照片信息等。这部分功能可以支撑应变片点位记录、现场复核和后续实验报告整理。

对于疲劳试验而言，点位管理不是简单的图片展示，而是整个数据链路的基础。点位编号需要与以下信息保持一致：

1. 仿真危险点编号；
2. 试验大纲中的测点编号；
3. 现场应变片编号；
4. 采集软件通道名称；
5. 后续数据文件中的列名或通道名；
6. 报告中的测点描述。

因此，点位管理模块后续应继续增强，重点不是增加视觉效果，而是提升编号一致性、通道映射、CAE 对应关系和数据追溯能力。

### 2.3 测试轮次与应变数据管理

项目已经具备测试轮次管理能力，能够记录不同循环次数或不同测试阶段下的测量数据。每个点位可以关联最大应变、最小应变、应变幅和应力幅等字段。

该能力基本符合疲劳台架试验的工作方式。实际试验中，通常会在若干循环次数后暂停或定期检查，记录关键点位的应变响应变化。系统能够按测试轮次组织数据，就可以为趋势分析、异常识别和疲劳损伤判断提供基础。

后续需要强化的是数据录入校验、重复轮次处理、单位说明、材料参数配置以及数据质量标记。

### 2.4 Excel / XLSX 数据导入能力

项目已经具备从 XLSX 文件导入测试数据的能力。该功能有助于承接 Dewesoft、Excel 汇总表或人工整理后的试验数据。

不过，当前导入流程仍偏直接写入，缺少足够的预检机制。对于实验数据系统而言，导入不是简单的文件读取，而应视为一次数据入库操作。系统需要在真正写入数据库前告知用户：哪些行可以导入、哪些点位无法匹配、哪些数据格式错误、哪些记录会覆盖已有数据。

因此，XLSX 导入建议从“直接导入”升级为“预检 + 确认导入”的模式。

### 2.5 趋势分析与异常识别能力

项目已经能够根据不同测试轮次的点位数据生成趋势图，并对部分异常变化进行识别。这说明系统已经开始从“数据存储工具”向“实验分析工具”过渡。

当前异常识别逻辑可以作为初步预警，但不宜作为严格的疲劳损伤判据。后续应将异常识别规则配置化，并结合绝对阈值、相对增长率、连续增长趋势、数据质量状态、CAE 预测值偏差等多种条件综合判断。

### 2.6 裂纹记录能力

项目已经包含裂纹记录功能，这对于疲劳试验后期非常重要。随着疲劳循环次数增加，如果某些区域出现裂纹、涂层开裂、焊缝异常或局部变形，系统需要将这些现象与点位数据、循环次数和照片记录关联起来。

后续建议裂纹记录与点位、测试轮次、照片、人工说明和处理措施形成完整闭环，而不是只作为独立备注存在。

### 2.7 数据导出能力

项目支持 JSON、CSV、ZIP 等导出形式。该能力对于实验资料归档、报告编写、跨系统传递和后续复盘都很重要。

建议后续进一步增加 Word/PDF 报告导出能力，尤其是针对单个项目生成标准化试验数据汇总报告，包括点位清单、测试轮次、异常点位、趋势图、裂纹记录和导出时间等信息。

## 3. 总体改进方向

PointBench 后续改进不应只围绕“增加更多页面”展开，而应围绕以下目标进行：

1. **数据可信**：导入的数据经过校验，修改有记录，删除可追溯；
2. **文件安全**：所有上传、解压、存储、导出操作都不能突破系统设定目录；
3. **流程闭环**：点位、照片、通道、测试轮次、异常、裂纹、报告之间存在明确关联；
4. **多人可用**：有基础权限体系，避免任何访问者都能修改或删除关键数据；
5. **可维护**：数据库结构可迁移，接口有测试，前后端错误处理统一；
6. **可扩展**：后续能支持更多项目、更多测点、更多试验类型和更多分析规则。

## 4. 安全性问题与整改建议

## 4.1 项目编号存在路径穿越风险

### 问题说明

当前后端多处使用 `project_id` 参与文件系统路径拼接。例如项目图片目录、裂纹图片目录、Dewesoft 文件目录、项目导出目录等，通常会根据项目编号构造路径。

如果 `project_id` 未经过严格限制，恶意用户可能构造包含 `../`、`..\\`、`/`、`\\` 等路径片段的项目编号，导致系统访问或删除预期目录之外的文件。

该问题在以下场景中风险较高：

1. 项目导入时复制图片文件；
2. 点位图片上传时保存文件；
3. 裂纹图片上传时保存文件；
4. 删除项目时递归删除项目目录；
5. 导出项目 zip 时读取项目目录；
6. Dewesoft 文件上传与删除。

其中风险最高的是删除项目逻辑。如果项目编号可控，并被用于 `shutil.rmtree()` 这类递归删除操作，理论上可能造成非项目目录被删除。

### 整改建议

项目编号应只允许安全字符，建议限制为：

```text
A-Z a-z 0-9 _ -
```

推荐规则：

```python
PROJECT_ID_PATTERN = r"^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$"
```

含义：

1. 必须以字母或数字开头；
2. 后续只允许字母、数字、下划线和短横线；
3. 最大长度限制为 64 个字符；
4. 不允许出现空格、斜杠、反斜杠、点号、中文路径符号等。

建议封装统一路径函数：

```python
from pathlib import Path
import re
from fastapi import HTTPException

PROJECT_ID_PATTERN = r"^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$"


def validate_project_id(project_id: str) -> str:
    if not re.fullmatch(PROJECT_ID_PATTERN, project_id):
        raise HTTPException(status_code=400, detail="非法项目编号")
    return project_id


def safe_project_dir(project_id: str) -> Path:
    validate_project_id(project_id)

    root = (STORAGE_DIR / "projects").resolve()
    path = (root / project_id).resolve()

    if path != root and root not in path.parents:
        raise HTTPException(status_code=400, detail="非法项目路径")

    return path
```

所有项目相关文件路径都应通过该函数生成，禁止在各个 router 或 service 中直接写：

```python
STORAGE_DIR / "projects" / project_id
```

### 验收标准

1. 输入 `../abc` 作为项目编号时，接口返回 400；
2. 输入 `abc/def` 作为项目编号时，接口返回 400；
3. 输入 `abc\\def` 作为项目编号时，接口返回 400；
4. 输入 `FRAME-FATIGUE-202606` 可以正常通过；
5. 删除项目时只能删除 `storage/projects/<project_id>` 目录；
6. 单元测试覆盖非法项目编号和正常项目编号两类情况。

## 4.2 上传文件名不应直接使用客户端 filename

### 问题说明

文件上传接口中，如果直接使用客户端传来的 `upload.filename` 作为保存路径的一部分，会存在路径穿越或文件覆盖风险。恶意客户端可以构造如下文件名：

```text
../../evil.zip
..\\..\\evil.zip
/absolute/path/file.zip
```

即使前端不会产生这类文件名，也不能信任客户端输入。后端必须假设所有上传字段都是不可信的。

### 整改建议

对于上传的 zip、图片、Dewesoft 文件等，后端不应直接使用原始文件名作为实际存储文件名。推荐做法是：

1. 使用系统生成的 UUID 作为物理文件名；
2. 原始文件名仅作为展示字段保存到数据库；
3. 保存前校验扩展名、MIME 类型和文件大小；
4. 所有文件必须保存到预期目录下。

示例：

```python
from pathlib import Path
from uuid import uuid4

original_name = Path(upload.filename or "upload.bin").name
suffix = Path(original_name).suffix.lower()
stored_name = f"{uuid4().hex}{suffix}"
stored_path = target_dir / stored_name
```

对于 zip 导入，甚至可以完全忽略原始文件名：

```python
zip_path = temp_dir / f"{uuid4().hex}.zip"
```

### 验收标准

1. 上传文件名包含 `../` 时，不会写出目标目录；
2. 上传同名文件不会覆盖已有文件；
3. 数据库中保留原始文件名和实际存储文件名；
4. 文件下载、预览和删除均使用数据库中的安全存储名。

## 4.3 Zip 解压需要防 Zip Bomb

### 问题说明

当前项目已经对 Zip Slip 路径穿越做了一定防护，这是正确方向。但仅防止路径穿越还不够。压缩包还可能存在 Zip Bomb 风险，即压缩包本身很小，但解压后体积极大，导致磁盘被写满、内存耗尽或服务卡死。

常见风险包括：

1. zip 内文件数量过多；
2. 单个文件解压后过大；
3. 所有文件解压后总体积过大；
4. 压缩比异常高；
5. 解压时一次性读取大文件导致内存占用过高。

### 整改建议

导入 zip 前应增加完整的安全检查。

建议默认限制：

| 限制项 | 建议值 | 说明 |
|---|---:|---|
| 上传 zip 文件大小 | 200 MB | 防止上传超大压缩包 |
| 解压后总大小 | 1 GB | 防止磁盘被写满 |
| 单个文件解压大小 | 50 MB | 防止单文件异常 |
| zip 内文件数量 | 5000 | 防止大量小文件耗尽资源 |
| 图片最大尺寸 | 12000 × 12000 | 防止超大图片解析风险 |

解压时不要使用一次性 `read()`，而应采用分块复制：

```python
import shutil

with zip_file.open(member) as source, open(target_path, "wb") as target:
    shutil.copyfileobj(source, target, length=1024 * 1024)
```

### 验收标准

1. 超过大小限制的 zip 被拒绝；
2. 文件数量超过限制的 zip 被拒绝；
3. 解压后总大小超过限制的 zip 被拒绝；
4. zip 内含路径穿越文件时被拒绝；
5. 大文件解压过程不会一次性占用大量内存；
6. 所有失败导入都能返回明确错误信息。

## 4.4 图片上传需要真实类型校验

### 问题说明

点位照片和裂纹照片属于系统核心资料。当前如果只根据扩展名判断图片类型，可能存在伪装文件风险。例如恶意用户可以将非图片文件改名为 `.jpg` 后上传。

虽然该系统主要用于内网，但仍应对上传内容进行基本检查，避免错误文件进入系统。

### 整改建议

图片上传建议增加以下限制：

1. 文件大小限制，例如单张图片最大 20 MB；
2. 扩展名白名单：`.jpg`、`.jpeg`、`.png`、`.webp`；
3. 使用 Pillow 或 python-magic 检查真实文件类型；
4. 检查图片尺寸，拒绝异常超大图片；
5. 重新生成安全文件名；
6. 可选：上传后统一转存为 JPEG/WebP，去除潜在异常元数据。

示例校验逻辑：

```python
from PIL import Image

try:
    image = Image.open(file_path)
    image.verify()
except Exception:
    raise HTTPException(status_code=400, detail="上传文件不是有效图片")
```

### 验收标准

1. 非图片文件改名为 `.jpg` 后无法上传；
2. 超大图片无法上传；
3. 图片保存名不包含用户原始路径；
4. 前端能显示上传失败原因。

## 4.5 缺少用户、权限和角色控制

### 问题说明

当前系统更接近单用户应用。只要能够访问后端接口，就可以执行导入、修改、删除等操作。如果部署在公司内网，任何能访问该地址的用户都可能修改或删除关键实验数据。

这对实验数据系统而言风险较高。实验数据具有归档和追溯价值，不能只依赖“大家不会乱点”来保证安全。

### 整改建议

建议至少建立三类角色：

| 角色 | 权限范围 |
|---|---|
| 查看者 | 查看项目、点位、趋势图、导出只读数据 |
| 录入者 | 新增测试轮次、录入测量数据、上传照片、添加裂纹记录 |
| 管理员 | 导入项目、修改项目基础信息、删除数据、管理用户和权限 |

短期内可以采用轻量方案：

1. 本地账号密码；
2. JWT 登录态；
3. 接口级权限装饰器；
4. 管理员初始化账户；
5. 内网部署时要求登录后访问。

后续如果公司有统一认证平台，再考虑接入企业 SSO 或 LDAP。

### 验收标准

1. 未登录用户不能访问写接口；
2. 查看者不能删除项目或修改测量数据；
3. 录入者不能删除项目；
4. 管理员可以执行高危操作；
5. 所有写操作记录操作者身份。

## 4.6 开发服务不应默认暴露到局域网

### 问题说明

前端开发服务和后端开发服务如果默认监听 `0.0.0.0`，则局域网内其他设备可能直接访问开发环境。开发服务通常没有经过生产级安全加固，不应作为默认启动方式。

对于 Vite、FastAPI 开发模式而言，默认开放到局域网只适合临时调试，不适合作为常规启动配置。

### 整改建议

默认开发脚本建议只监听本机：

```bash
vite --host 127.0.0.1
uvicorn main:app --host 127.0.0.1
```

如确实需要手机或其他设备访问，再单独提供局域网调试脚本：

```json
{
  "scripts": {
    "dev": "vite --host 127.0.0.1",
    "dev:lan": "vite --host 0.0.0.0"
  }
}
```

后端也类似：

```bash
python start.py --host 127.0.0.1
python start.py --host 0.0.0.0 --lan
```

### 验收标准

1. 默认启动只允许本机访问；
2. 局域网访问必须使用显式命令；
3. README 中明确说明局域网调试风险；
4. 生产部署不使用 Vite 开发服务器。

## 4.7 Python 上传解析依赖建议升级

### 问题说明

项目使用 `python-multipart` 处理文件上传。该类依赖属于上传链路的关键依赖，建议保持相对较新的安全版本。

### 整改建议

建议将依赖约束提高到：

```text
python-multipart>=0.0.26
```

同时建议后续采用依赖锁定机制，避免不同机器安装到不同版本。

### 验收标准

1. `requirements.txt` 或锁文件中版本满足要求；
2. 文件上传接口正常；
3. 后端测试覆盖 zip 上传、图片上传、Dewesoft 上传。

## 5. 数据完整性问题与整改建议

## 5.1 引入数据库迁移体系

### 问题说明

当前项目如果主要依赖 SQLAlchemy `create_all()` 初始化数据库，短期开发方便，但不适合长期演进。后续一旦增加字段、修改表结构或引入用户权限，就会遇到旧数据库无法平滑升级的问题。

例如后续可能增加：

1. 用户表；
2. 角色表；
3. 审计日志表；
4. 项目状态字段；
5. 材料参数字段；
6. 通道映射表；
7. CAE 映射表；
8. 软删除字段；
9. 数据质量标记字段。

如果没有数据库迁移工具，这些变化只能通过手工改库或删除重建数据库完成，不适合真实实验数据沉淀。

建议引入 Alembic。

```text
backend/
  alembic/
    versions/

  alembic.ini
```

2. 不允许通过删除数据库解决结构变化；
3. 启动时可以检查当前数据库版本；
4. 部署前执行 `alembic upgrade head`。

### 验收标准

1. 项目包含 Alembic 配置；
2. 当前数据库结构有初始 migration；
3. 新增字段可以通过 migration 更新旧数据库；
4. README 中说明数据库升级方式。

## 5.2 TestRun 需要唯一性约束

### 问题说明

测试轮次是实验数据的横向组织单位。如果同一项目中允许出现多个相同循环次数或相同名称的测试轮次，趋势分析和数据对比会变得混乱。

例如同一项目中同时存在两个：

```text
cycle_count = 400000
```

系统在绘制趋势图时就无法明确哪个数据代表 40 万次循环后的正式结果。

### 整改建议

建议根据业务规则增加唯一性约束。

推荐至少增加：

```text
(project_db_id, cycle_count) unique
```

如果测试轮次名称也要求唯一，则增加：

```text
(project_db_id, run_name) unique
```

如果确实允许同一循环次数多次测试，则需要额外增加 `test_index` 或 `run_type` 字段，例如：

```text
cycle_count = 400000
run_type = repeat_check
test_index = 2
```

但默认不建议允许模糊重复。

### 验收标准

1. 同一项目中重复循环次数会被拒绝或明确提示覆盖；
2. 趋势图不会因重复轮次出现顺序混乱；
3. XLSX 导入遇到重复轮次时有明确策略。

## 5.3 测量数据需要更强的数值校验

### 问题说明

应变数据是系统分析的核心。如果数据录入阶段允许非法值进入数据库，后续趋势图、异常判断和报告结论都会受到影响。

常见问题包括：

1. 循环次数为负数；
2. 循环次数不是整数；
3. 最大应变小于最小应变；
4. 应变值超出合理范围；
5. 空值和 0 被混淆；
6. 前端传入 `NaN`、`Infinity` 等异常数值；
7. 应变单位不明确。

### 整改建议

后端 schema 中应增加强校验。

示例：

```python
from pydantic import BaseModel, Field, field_validator

class MeasurementInput(BaseModel):
    cycle_count: int = Field(ge=0, le=10_000_000)
    max_strain: float | None = Field(None, ge=-100000, le=100000)
    min_strain: float | None = Field(None, ge=-100000, le=100000)

    @field_validator("max_strain")
    @classmethod
    def check_finite(cls, v):
        if v is not None and not math.isfinite(v):
            raise ValueError("应变值必须为有限数值")
        return v
```

同时增加业务校验：

```python
if max_strain is not None and min_strain is not None:
    if max_strain < min_strain:
        raise HTTPException(status_code=400, detail="最大应变不能小于最小应变")
```

前端也应同步校验，避免用户提交明显错误数据。

### 验收标准

1. 负循环次数无法保存；
2. 最大应变小于最小应变时无法保存；
3. `NaN`、`Infinity` 无法保存；
4. 前端在保存前显示明确错误；
5. 后端即使绕过前端也能拒绝非法数据。

## 5.4 XLSX 导入应增加预检流程

### 问题说明

XLSX 导入属于批量写入操作，风险高于单条录入。当前如果导入过程直接写入数据库，用户很难在导入前发现以下问题：

1. 点位编号无法匹配；
2. Excel 列名错误；
3. 单元格为空；
4. 数值格式错误；
5. 同一文件中存在重复点位；
6. 导入数据会覆盖已有数据；
7. 循环次数重复；
8. 单位与系统预期不一致。

### 整改建议

建议将 XLSX 导入改为两步：

```text
POST /api/measurements/import-xlsx/preview
POST /api/measurements/import-xlsx/confirm
```

预检接口返回：

```json
{
  "total_rows": 120,
  "valid_rows": 108,
  "invalid_rows": 12,
  "unmatched_points": ["P021", "P022"],
  "duplicate_points": ["P005"],
  "will_overwrite": true,
  "errors": [
    {
      "row": 15,
      "field": "max_strain",
      "message": "最大应变不是有效数字"
    }
  ]
}
```

确认导入时，用户需要明确选择：

1. 忽略错误行；
2. 中止全部导入；
3. 覆盖已有数据；
4. 只导入新增数据。

### 验收标准

1. Excel 错误不会直接污染数据库；
2. 用户可以在导入前看到错误清单；
3. 覆盖已有数据必须明确确认；
4. 导入完成后生成导入报告。

## 5.5 Dewesoft 导入记录与测量数据关系需要明确

### 问题说明

Dewesoft 文件导入后，如果系统生成了测试轮次和测量数据，那么导入记录、原始文件、生成数据之间应有明确关系。

如果用户删除了 Dewesoft 导入记录，但生成的测量数据仍然存在，会造成语义不一致。用户可能认为“导入记录已删除，所以数据也不再参与分析”，但趋势图中数据仍然存在。

### 整改建议

建议建立以下关系：

```text
DewesoftImportRecord
  -> TestRun
  -> MeasurementRecord
```

并为导入记录设计状态：

```text
pending
parsed
confirmed
disabled
deleted
failed
```

推荐采用软删除策略：

1. 删除导入记录时，不立即删除原始数据；
2. 标记该导入记录为 disabled 或 deleted；
3. 由该导入产生的数据默认不参与趋势分析；
4. 管理员可以恢复或彻底清理。

### 验收标准

1. Dewesoft 导入记录能追溯到生成的数据；
2. 删除导入记录时，系统明确提示影响范围；
3. 趋势分析能排除被禁用导入产生的数据；
4. 原始文件不会被误删。

## 5.6 删除操作建议改为软删除

### 问题说明

实验数据具有长期追溯价值。项目、点位、照片、测试轮次、裂纹记录等数据一旦被硬删除，后续很难恢复，也无法解释报告数据为何变化。

当前如果删除操作直接删除数据库记录或磁盘文件，误操作风险较高。

### 整改建议

建议为核心表增加软删除字段：

```text
deleted_at
deleted_by
delete_reason
```

对于图片文件，建议数据库中标记删除，但物理文件延迟清理。只有管理员执行维护命令时，才真正清理磁盘文件。

删除流程建议：

1. 普通删除：软删除；
2. 回收站：可查看和恢复；
3. 彻底删除：仅管理员可执行；
4. 删除记录写入审计日志。

### 验收标准

1. 删除图片后可以恢复；
2. 删除项目后不会立即物理清空所有文件；
3. 审计日志记录删除人、删除时间和原因；
4. 普通用户无彻底删除权限。

## 6. 分析逻辑与实验业务改进建议

## 6.1 材料参数不应固定为单一钢材

### 问题说明

当前应力换算逻辑主要基于线弹性关系：

$$
\sigma = E \cdot \varepsilon
$$

如果应变单位为 $\mu\varepsilon$，则：

$$
\sigma = E \cdot \varepsilon \cdot 10^{-6}
$$

对于普通钢材，如果取：

$$
E = 206000\ \text{MPa}
$$

则：

$$
1\ \mu\varepsilon \approx 0.206\ \text{MPa}
$$

这种计算可用于普通钢材、小变形、单轴线弹性近似。但如果测点位于焊缝附近、复杂应力状态区域、局部塑性区域或非钢材部件，直接使用固定弹性模量可能导致误判。

### 整改建议

建议增加材料参数配置。

项目级材料字段：

```text
material_name
elastic_modulus_mpa
poisson_ratio
yield_strength_mpa
tensile_strength_mpa
strain_unit
stress_unit
```

点位级可覆盖字段：

```text
point_material_name
point_elastic_modulus_mpa
stress_conversion_enabled
```

前端显示时应明确标注：

```text
应力幅由应变幅按 E=206000 MPa 线弹性换算得到，仅用于趋势参考。
```

### 验收标准

1. 每个项目可以配置材料参数；
2. 不同项目可以使用不同弹性模量；
3. 趋势图标注应力换算参数；
4. 导出报告中包含材料参数说明。

---

## 6.2 异常判定规则需要配置化

### 问题说明

当前异常识别逻辑可以作为初步提示，但仍偏简单。如果只根据“相对上一轮增长超过 20%”或“连续 3 次上升”判断异常，可能出现误报或漏报。

误报场景：

1. 初始应变幅很小，轻微波动也可能超过 20%；
2. 传感器零漂导致趋势上升；
3. 工况载荷略有变化；
4. 贴片或线缆状态变化。

漏报场景：

1. 应变幅绝对值已经很高，但增长率不明显；
2. 单次突增但不满足连续上升；
3. 与 CAE 预测偏差很大但未超过增长阈值；
4. 人工观察到裂纹但应变变化不明显。

### 整改建议

建议将异常判断拆分为多种规则：

1. 绝对阈值规则；
2. 相对增长率规则；
3. 连续增长规则；
4. 与 CAE 预测偏差规则；
5. 人工标记规则；
6. 数据质量异常规则。

示例配置：

```json
{
  "strain_amplitude_warning": 300,
  "strain_amplitude_danger": 500,
  "relative_growth_warning": 0.2,
  "continuous_growth_count": 3,
  "minimum_effective_growth": 50,
  "cae_deviation_ratio": 0.3
}
```

异常字段建议拆分：

```text
auto_abnormal
manual_abnormal
abnormal_level
abnormal_reasons
data_quality_flags
```

### 验收标准

1. 异常规则可以在项目级配置；
2. 自动异常和人工异常分开显示；
3. 每条异常都有明确触发原因；
4. 用户可以将误报标记为忽略；
5. 导出报告中包含异常规则说明。

## 6.3 趋势分析应提供多种统计口径

### 问题说明

疲劳试验中的“危险点”不是单一概念。不同分析目的需要不同统计口径。

例如：

| 统计口径 | 说明 |
|---|---|
| 最新轮次最大值 | 判断当前最危险点 |
| 历史最大值 | 找整个试验过程中曾经达到最大响应的点 |
| 增长率最大 | 找潜在损伤演化点 |
| 连续上升点 | 找需要重点复核的点 |
| 与 CAE 偏差最大 | 判断试验与仿真一致性 |
| 人工异常点 | 结合现场观察结果 |

如果系统只显示一种 Top 列表，容易导致用户误解。

### 整改建议

项目概览页建议拆分为以下卡片：

1. 最新轮次应变幅 Top 10；
2. 最新轮次应力幅 Top 10；
3. 历史最大应力幅 Top 10；
4. 相对增长率 Top 10；
5. 连续上升点位；
6. 人工标记异常点位；
7. 数据质量异常点位；
8. 与 CAE 偏差较大点位。

### 验收标准

1. 不同统计口径在界面上明确区分；
2. 每个 Top 列表显示对应测试轮次和循环次数；
3. 用户可以点击点位进入详情；
4. 导出报告中保留统计口径说明。

## 6.4 增加数据质量标记

### 问题说明

实验数据异常不一定代表结构发生疲劳损伤，也可能来自测试系统本身。例如：

1. 应变片脱胶；
2. 线缆接触不良；
3. 通道接错；
4. 桥路配置错误；
5. 零漂异常；
6. 重贴应变片；
7. 采集软件通道名称错误；
8. 测点照片与编号不一致。

如果系统没有数据质量标记，后续分析容易把测试系统异常误判为结构异常。

### 整改建议

为点位和测量记录增加数据质量字段。

点位级状态：

```text
normal
suspicious
disabled
replaced
wire_issue
sensor_failed
```

测量记录级标记：

```text
zero_drift
noise_high
manual_corrected
channel_changed
sensor_replaced
load_condition_changed
```

前端趋势图中应支持显示这些事件节点，例如某一轮次点位被重贴或换线。

### 验收标准

1. 用户可以为点位设置状态；
2. 用户可以为某一轮测量数据添加质量标记；
3. 趋势图显示关键事件；
4. 异常识别可以排除质量异常数据。

## 7. 前端功能与交互改进建议

## 7.1 点位较多时需要批量趋势接口

### 问题说明

如果前端对每个点位单独请求趋势数据，会形成 N+1 请求问题。点位数量较少时影响不明显，但当项目包含几十到几百个点位时，页面加载速度会明显下降。

后端增加批量趋势接口：

```text
GET /api/projects/{project_id}/trends
```

返回所有点位的摘要趋势：

```json
{
  "project_id": "FRAME-FATIGUE-202606",
  "points": [
    {
      "point_id": "P001",
      "latest_cycle_count": 400000,
      "latest_strain_amplitude": 123.4,
      "latest_stress_amplitude": 25.4,
      "growth_rate": 0.18,
      "is_abnormal": false
    }
  ]
}
```

点位详情页再单独请求完整历史趋势。

### 验收标准

1. 项目概览页只需 1 次趋势摘要请求；
2. 点位详情页才请求单点完整趋势；
3. 100 个点位时页面加载速度仍可接受。

## 7.2 前端包体积需要优化

### 问题说明

当前前端构建产物主 JS 较大。主要可能来自图表库、Excel 处理库和页面未懒加载。

包体积过大会导致：

1. 首屏加载慢；
2. 局域网弱设备访问体验差；
3. 后续功能增加后进一步膨胀；
4. 浏览器解析 JS 时间增加。

### 整改建议

建议采取以下措施：

1. 路由级懒加载；
2. ExcelJS 动态导入；
3. 图表组件按需加载；
4. 低频功能拆分 chunk；
5. 使用 bundle analyzer 检查依赖体积。

示例：

```tsx
import { lazy } from "react";

const ProjectOverviewPage = lazy(() => import("./pages/ProjectOverviewPage"));
```

ExcelJS 动态导入：

```ts
const ExcelJS = await import("exceljs");
```

或者直接由后端生成 Excel 模板，前端只负责下载。

### 验收标准

1. 首屏 bundle 明显下降；
2. Excel 相关代码不进入首屏包；
3. 路由切换正常；
4. 构建无 chunk size warning 或 warning 明显减少。

## 7.3 危险操作需要统一确认

### 问题说明

删除项目、删除图片、删除测试轮次、删除裂纹记录等操作具有不可逆或高影响特征。如果前端没有统一确认机制，误操作风险较高。

### 整改建议

所有危险操作统一使用确认弹窗，并根据危险程度分级。

普通危险操作：

```text
确认删除该图片？删除后可在回收站恢复。
```

高危操作：

```text
该操作将删除整个项目及其关联数据。请输入项目编号以确认删除。
```

建议高危操作增加二次确认：

1. 弹窗说明影响范围；
2. 用户输入项目编号；
3. 后端检查权限；
4. 后端写审计日志。

### 验收标准

1. 删除图片前有确认；
2. 删除项目前需要输入项目编号；
3. 删除测试轮次前提示影响趋势图；
4. 取消删除不会产生任何数据变化。

### 问题说明

实验数据录入时，用户很容易出现单位、正负号、最大最小值、空值等错误。前端应尽可能在保存前发现问题，而不是完全依赖后端报错。

6. 覆盖已有数据时提示；

### 验收标准

1. 明显错误无法提交；
2. 录入页面显示单位；
3. 应变幅和应力幅实时更新；

## 8. 后端工程质量改进建议

## 8.1 增加统一错误码

### 问题说明

如果后端只返回中文错误字符串，前端很难稳定处理不同错误。后续如果要做国际化、错误分类或自动提示，也会受限。

### 整改建议

建议统一错误格式：

```json
{
  "code": "INVALID_PROJECT_ID",
  "message": "项目编号非法",
  "details": {}
}
```

常见错误码：

```text
INVALID_PROJECT_ID
PROJECT_NOT_FOUND
PROJECT_ALREADY_EXISTS
INVALID_ZIP_FILE
ZIP_TOO_LARGE
ZIP_UNSAFE_PATH
INVALID_IMAGE_FILE
MEASUREMENT_VALIDATION_FAILED
PERMISSION_DENIED
IMPORT_PREVIEW_EXPIRED
```

### 验收标准

1. 后端错误响应结构统一；
2. 前端根据 code 显示提示；
3. 日志中记录 code 和上下文；
4. README 中列出常见错误码。

审计日志：

1. 创建项目；
2. 导入项目；
3. 修改点位；
4. 上传图片；
5. 删除图片；
6. 创建测试轮次；
7. 修改测量数据；
8. 删除测试轮次；
9. 导出数据；
10. 修改异常标记。

审计日志表建议字段：

```text

action
object_type
object_id
project_id
before_snapshot
after_snapshot
created_at
ip_address
user_agent
```

### 验收标准

1. 所有写操作都有审计记录；
2. 管理员可以查看项目操作历史；
3. 删除操作记录删除原因；
4. 导出操作也被记录。

## 8.3 增加临时文件清理机制

### 问题说明

导入预览、zip 解压、项目导出、图片处理等过程都会产生临时文件。如果没有清理机制，长期运行后会占用大量磁盘空间。

### 整改建议

建议建立统一临时目录：

```text
storage/temp/imports
storage/temp/exports
storage/temp/uploads
```

清理策略：

1. 导入预览超过 24 小时自动清理；
2. 导出文件下载后清理；
3. 服务启动时扫描过期临时文件；
4. 提供维护命令手动清理。

示例命令：

```bash
python scripts/cleanup_storage.py --older-than 24h
```

### 验收标准

1. 临时文件不会长期堆积；
2. 导出文件下载后可清理；
3. 清理任务不会误删项目正式文件；
4. 清理过程有日志记录。

## 8.4 SQLite 可保留，但应支持 PostgreSQL

### 问题说明

SQLite 适合单机试用和早期开发，但多人同时写入、长期部署和权限体系扩展时，建议使用 PostgreSQL。

SQLite 的主要限制：

1. 并发写入能力有限；
2. 多用户场景下容易出现写锁；
3. 权限、备份、监控能力较弱；
4. 不适合长期承载大量实验项目。

### 整改建议

保留 SQLite 作为默认开发数据库，同时通过环境变量支持 PostgreSQL。

示例：

```env
DATABASE_URL=sqlite:///./pointbench.db
DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/pointbench
```

### 验收标准

1. 本地开发可继续使用 SQLite；
2. 部署环境可切换 PostgreSQL；
3. Alembic migration 对两类数据库均可执行；
4. README 中说明数据库配置方式。

## 9. 依赖与供应链改进建议

## 9.1 Python 依赖需要锁定

### 问题说明

如果 `requirements.txt` 中大量使用 `>=`，不同电脑可能安装到不同版本。后续在公司内网离线部署时，这会导致环境不可复现。

### 整改建议

建议使用以下任一方式锁定依赖：

1. `pip-tools`；
2. `uv`；
3. `poetry`；
4. `requirements.lock`。

推荐简单方案：

```text
requirements.in   # 手工维护直接依赖
requirements.txt  # 自动生成锁定版本
```

生成命令：

```bash
pip-compile requirements.in -o requirements.txt
```

### 验收标准

1. 新环境安装依赖版本一致；
2. 离线部署可以根据锁文件准备 wheel 包；
3. 依赖升级有明确记录。

---

## 9.2 前端依赖需要定期审计

### 问题说明

前端依赖数量通常较多，间接依赖可能存在安全告警。项目中涉及 Excel 处理、图表渲染、构建工具等依赖，应定期审计。

### 整改建议

建议在开发流程中增加：

```bash
npm audit
npm outdated
```

CI 中可以加入：

```bash
npm audit --audit-level=high
```

对于 moderate 级别告警，可以结合实际风险评估，不一定立即阻断构建。但 high 和 critical 应优先处理。

### 验收标准

1. README 中说明依赖审计方式；
2. 高危依赖升级有记录；
3. 低频大依赖尽量动态加载；
4. 前端构建可稳定复现。

## 14. 最终结论

PointBench 当前已经具备较清晰的业务方向和可运行的核心流程，能够支撑实验室内网 MVP 试用。它的价值不只是管理照片和表格，而是有潜力成为“试验点位记录、测试数据沉淀、趋势分析、异常追溯、报告输出”的一体化工具。

但现阶段项目还不能直接按生产系统部署。最需要优先处理的不是继续堆功能，而是补齐安全边界和数据可信度：

1. 防止路径穿越；
2. 防止恶意或异常上传文件；
3. 防止误删除；
4. 防止错误实验数据直接入库；
5. 保证数据修改可追溯；
6. 保证后续数据库结构可迁移；
7. 保证核心流程有自动化测试。

建议后续开发按“安全边界 → 数据可靠性 → 分析能力 → 多人协作”的顺序推进。这样可以避免项目在功能越来越多之后，因为底层数据结构和安全边界不稳而被迫大规模返工。
